## 1. Architecture facts that matter for i18n

- Plain JavaScript ES modules, **no build step and no bundler**: 36 files in `js/`, about 1,536 lines of `index.html`, about 4,400 lines of `css/styles.css`.
- Firebase: Auth (Google), Firestore with offline persistence, and Cloud Functions in `functions/index.js` (`parseDictation`, the checklist reminder scheduler, `previewReminders`, `sendTestNotification`).
- PWA. `service-worker.js` precaches every file in `PRECACHE_URLS`, each with a `?v=<build>` cache-buster. Every build bumps `?v=` in `index.html`, `service-worker.js` (`VERSION`, `SHELL_URL`, `PRECACHE_URLS`) and `manifest.json`.
- The app is **offline-first** (SPEC.md Section 13). Anything i18n loads must be precached and must not need a network fetch.
- The page stays invisible until `body.app-ready` is set (`js/app.js` `revealApp()`, two animation frames plus 150 ms). Static translations can be applied before that point, so English users never see a flash of German.
- The core logic compares **internal keys**, not visible labels. Examples are `'stueck'`, `'weekly'`, `data-tab`, `data-unit` and `data-horizon`. No code compares `textContent` against German text. **Translating labels therefore does not break behaviour.**
- `SPEC.md` Section 2 says "UI language: **German**". It must be updated when i18n lands.

## 3. Proposed architecture

1. **`js/i18n.js`**: a small home-grown module of about 80 lines, with no library. i18next and similar libraries would need a CDN fetch or a build step, which conflicts with offline-first. It provides:
   - `t(key, params)` with `{name}` placeholders.
   - Plurals via `Intl.PluralRules`, with keys like `tasks_due.one` and `tasks_due.other`.
   - `fmtNumber()` and `fmtDate()`, which wrap `Intl` with the active locale.
   - `getLang()` / `setLang()`.
   - `applyStatic(root)`, which handles `data-i18n="key"` and `data-i18n-attr="placeholder:key;title:key"`.
   - **Fallback:** a key missing in `en` falls back to `de`, and a key missing in both shows the key name and logs a console warning.
2. **`js/locales/de.js` and `js/locales/en.js`**: plain ES-module objects. They load synchronously, need no async JSON fetch, and are precached by the service worker.
3. **Semantic, namespaced keys** such as `nav.dashboard`, `stock.checkin.title` and `confirm.log.clear`. Do not use the German text as the key.
4. **Storage of the choice.** `localStorage['erdkeller.lang']` is primary because it works before sign-in and offline. The choice is mirrored to `/users/{uid}.lang` so the server can send push notifications in each person's language. The existing rule already lets users update their own doc as long as they don't change `role`, so **no `firestore.rules` change is needed**.
5. **Switching = save + `location.reload()`.** Re-rendering about 30 independently stateful modules live would be fragile. The reload works offline because the service worker serves the shell. Show a `confirm()` first if a check-in, check-out or dictation flow is open, because the reload loses it.
6. **The switch button** sits in `.sidebar-account` next to `#account-toggle-sidebar` (bottom left, tablet layout). It shows "DE" / "EN" and toggles on tap. Phone placement is still an open question (Section 7).
7. **Server side:** `buildNotificationText(frequency, breakdown, lang)` with per-language label maps. The scheduler reads each recipient's `/users/{uid}.lang` and defaults to `de` when the field is missing. It must never fail on a missing or unknown value.
8. **Every build that adds a file** must add it to `PRECACHE_URLS` in `service-worker.js`, with the `?v=` bump.

## 5. Risks, traps and mitigations

1. **User data stays German. This is the main pushback.** In English mode the UI would read "Check in → Konserven → Nudeln". Translating data would need a second copy of every field, a way to keep both in sync, and a decision on who maintains it. **Recommendation: translate the UI only.**
2. **"German text must not change."** Moving about 1,000 strings by hand risks typos, whitespace changes and lost entities (`&amp;`, `&lt;`, `&nbsp;`, `‹`, `…`, emoji).
   - *Mitigation:* script-assisted extraction, plus a verification script that confirms every German literal removed from code or HTML reappears **byte-identical** in `de.js`.
   - Keep the emoji and glyphs inside the strings exactly as they are now.
   - There is no Firebase emulator setup, so signed-in screens cannot be compared automatically by screenshot. A manual click-through in German is needed on every build.
3. **Sentences built from German fragments**, e.g. `Aufgabe${n===1?'':'n'}` and `FREQ_LABELS_ADJ + ' Wartung'`. English word order and plurals differ, so these need whole-sentence templates with placeholders and `Intl.PluralRules`.
4. **`innerHTML` with translated strings** can break markup or allow injection. Use `textContent` by default and allow markup only for explicitly flagged keys.
5. **Number format.** en-US shows `1,234.5`, the reverse of German. Input parsing accepts both `,` and `.`, so a US user typing `1,5` gets 1.5. *Recommendation:* display in en-US format and leave parsing unchanged.
6. **The button placement only exists on tablet.** The bottom-left sidebar is tablet-only. Phones have the avatar at the top right in `.topbar-account`, and the sign-in screen has no avatar at all.
7. **Offline cache.** A new file missing from `PRECACHE_URLS` breaks offline use. Check this on every build.
8. **Push notifications are generated on the server**, per recipient. Until a user's `lang` is saved they receive German. The scheduler must tolerate a missing `lang`.
9. **Dictation and AI are German-centric** (`de-DE` recognizer, German prompts, German catalogue). English speech matched against German product names will match worse.
10. **Domain terms need a fixed glossary** before translating, otherwise the English will be inconsistent across 30 files. The terms are: Einlagern, Entnehmen, Diktieren, Bestand, Bestandsliste, MHD, Einkaufsliste, Funkstille, Verbindung, Stk, g/P/T, kcal/P/T, Wartung, Krisenvorsorge, Rückgängig.
11. **`SPEC.md` says the UI is German.** Update it, or future sessions will follow the old rule.
12. **Scale and regression risk.** This touches almost every file. Keep it to one build per phase, with no feature work mixed in, so each build can be reverted on its own.
13. **Live switching vs reload.** A reload loses half-finished flows. Mitigate with the confirm dialog (Section 3, item 5).
14. **Text length.** English is usually shorter than German, so this is low risk. Still check the segmented controls, the dashboard unit toggle and the big buttons.

*Side note, outside the i18n scope:* the `/users/{uid}` update rule lets members change their own `recipientSlug`. This is pre-existing and harmless in practice.

### 8.1 What counts as data (confirmed from the code)

All of the following live in Firestore and are editable in the app, not hardcoded:
- **Types, categories and subcategories**: `/config/taxonomy`, edited in Admin → Taxonomie.
- Products (`/products`), storage locations, year colours, targets, checklists and their items, contacts, notes, recipes.

Caveats for an English dataset:
- **The dataset is shared by the whole household.** It is not per language. Renaming categories to English changes them for every user, including those whose UI is German.
- **Stock batches store a frozen copy of the names.** Each `/stockItems` doc stores a copy of `type` / `category` / `subcategory` names taken at check-in (`js/stock-checkin.js:691`). Bestandsliste filtering, sorting and the CSV/PDF exports read that copy. Renaming the taxonomy leaves old batches showing the old German names. An English dataset therefore needs a one-off "re-sync names on all batches" step. The same mechanism already exists per product since Build 184.
- **The AI is told which language to use for new product names.** `APP_LANGUAGE = 'Deutsch'` in `functions/index.js:67` sets the language for new product names proposed by dictation and photo. This should follow the **dataset** language, not the UI language, or the catalogue ends up mixed.
- **A few data-looking labels are actually hardcoded UI text** and will be translated with the UI: "Wasser" (`dashboard.js:546`, the class button in `taxonomy.js:296`), Kohlenhydrat/Protein/Fett (macro keys stay German internally) and "Produktziele".

### 8.2 Switching dictation language with the toggle

What it takes:
- **Client.** `js/dictate.js:246` `recognizer.lang` follows the UI language (`de-DE` / `en-US`). This is a one-line change. Android Chrome's speech recognition already needs a connection, and so does the AI call.
- **Server.** `parseDictation` receives `lang` in `request.data`. The prompt is told the transcript may be English. The existing instructions stay in German, which Claude handles fine. The product-name language stays tied to the dataset (8.1).
- **Errors.** The `HttpsError` messages become error codes that the client translates.
- **Deployment.** This needs `firebase deploy --only functions`, run by Markus.
- **Effort:** small, about half a build, plus real-device testing with English sentences.

Risks:
- English speech is matched against German product names ("canned tomatoes" → "Gepellte Tomaten"). Claude translates this well, but matching will be somewhat less reliable than German-to-German.
- New products must still be proposed in German, otherwise the catalogue becomes mixed.
- Spoken quantities with imperial units ("two pounds") are only safe if 8.3 is done.

### 8.3 Imperial units and US dates

**Dates: cheap, low risk.**
- The app's main date granularity, MM/YYYY, is identical in the US.
- Full dates (person "joined", backup timestamps, notification settings) switch to MM/DD/YYYY automatically once formatting goes through `Intl` with `en-US`.
- The weekday dropdowns are Monday-first, and the scheduler stores 1 = Monday … 7 = Sunday. Only the labels get translated. Keep Monday-first ordering, because changing the stored numbering would break existing schedules.

**Units: a separate, sizeable project.**
- Everything is stored metric:
  - kg/l stock totals.
  - Free-text product `content` such as "500 g" or "1 l". The parser takes the leading number and *assumes grams/ml* (`dashboard.js:384`, `pdf-export.js:546`, `recipes.js:92`).
  - Targets in kg or g per person per day, water in L per person per day.
  - kcal, which is the same in the US.
- About **200 unit-touching places**: `dashboard.js` (~62), `targets.js` (~55), `pdf-export.js` (~33), `index.html` (~20), `stock-checkin.js`, `dictate.js`, `planning.js`, `stock-table.js`.
- Approach: keep storage metric and convert only for display and input (lb/oz, gal/fl oz).

Risks:
1. **The content parser silently misreads imperial input.** "16 oz" is read as 16 g, so dashboard totals are off by 28×. This needs a unit-aware parser (g, kg, oz, lb, ml, l, fl oz, gal) first.
2. **Rounding drift** on edit round trips (2 lb → 0.907 kg → back) and in per-person-per-day targets.
3. **Weight oz vs fluid oz** is ambiguous, and the existing "1 L ≈ 1 kg" simplification carries over.
4. Shared household data shown in different units on different phones can confuse people talking about it.
5. AI dictation output would need to produce or understand imperial amounts.

**Recommendation.**
- Make units a **separate setting from language**, since English speakers in Europe use metric.
- Do it as its own project **after** i18n. i18n stays metric.
- Include US date formatting with English, because it is essentially free.

### 8.4 Workflow (explained)

- The repo has one live branch, `claude/project-onboarding-mdzoen`. GitHub Pages serves it directly (SPEC.md Section 18), so **every push there is live** on all devices at next open. There is no staging environment.
